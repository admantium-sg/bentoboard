## 2. Method

The run delegated **all** web verification to three subagents (5 claims each, at most 2 running in parallel), so no raw search page entered the main-agent context. Each subagent wrote a compact result file and returned only a one-line tally:

- `fact_check_work/2026-11-05/2026-11-05_batch_1.md` — C1–C5 (releases)

Per-claim budget: max 2 web searches + 2 direct URL fetches, 10 searches per batch, 30 searches for the whole run (cap respected). `verification_status.json` was written after every batch of 5 so a partial run would not repeat work.

No claim was found to be false. All three "partial" verdicts are **timestamp attribution errors**: the accumulator had recorded GitHub's `updated_at` instead of `published_at`, or had attributed a merge-commit time to a release.

## 6. Trend analysis

- **Correction rate this run: 0 %.** No claim was contradicted; the corpus's first clean run in at least three cycles (previous: 8.2 % cumulative, 11 % last run). The 3 partial verdicts are collection-timestamp defects, not factual errors.
- **`updated_at` vs `published_at` is now the dominant error mode.** It produced 2 of 3 partial verdicts in this run alone. A fix in the accumulator's release-fetching step — reading `published_at` from the release object and ignoring `updated_at` — would eliminate this class outright. It is worth checking whether the same mistake is present in the 2026-11-01 to 2026-11-04 archived sections (up to 40 release timestamps, none yet checked).
- **GitHub issue-title claims remain the least verifiable class.** The 375-issue in-window harvest in the 2026-11-05 section is user-reported, unreproduced, and — because GitHub's REST search API is 403-rate-limited — was collected from the HTML index rather than a structured API. These should stay in the pending queue at low priority; each would need the issue body, not just the title, to be worth checking.
- **Secondary coverage of the 2026-11-04 announcement cluster is strong.** Six independent outlets (TechCrunch, The Decoder, itmunch, startupfortune, iTWire, aicoder.com) plus five first-party pages covered the same-day M&A and security stories, which is why those 12 claims verified at 100 %.
- **Nightly/rolling builds cannot be verified as claimed.** A rolling `nightly` tag has no stable `published_at`; any finding that cites one is unverifiable by construction. Recommend the accumulator stop asserting publication timestamps for rolling tags and cite the commit hash instead.
